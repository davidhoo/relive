# 统一身份匹配引擎：增量聚类与人物合并推荐

日期：2026-09-08  
执行对象：Cursor  
状态：本地实现与测试已完成（见 `2026-09-08-people-identity-primary-delivery.md`）；未部署、未切换生产 primary。

## 1. 目标与交付边界

实现真正的 `people.identity_profile_mode: primary`，使增量聚类与人物合并推荐共同使用统一的多中心身份匹配引擎。候选召回、证据聚合、打分、约束和原因解释共用实现；自动聚类和人工推荐使用不同阈值及证据要求。新引擎不可用时等待恢复，不隐式切换旧算法。保留完整自动归属记录和按批次撤销能力。

本修订取代旧版“只接管聚类、推荐维持混合路径、故障时自动用旧算法兜底”的方案。验收必须同时覆盖两条业务链路，不能仅统一命名、接口或 embedding 校验函数。

本任务的目标是交付可上线的功能，不继续把“样本不足”作为无限期停留在 rescue 的理由。上线评估要指出具体缺陷和影响；没有发现缺陷不等于已经证明准确率。

默认执行范围：代码、迁移、测试、数据库副本验证、操作文档。允许读取已配置的 NAS 状态；连接不可用时说明缺失证据，继续本地实现。不得因缺少 NAS 连接而停止全部开发。

本文件本身不授权修改 NAS 配置、部署、重启生产服务或撤销生产数据。完成本地工作和可审阅结果后，提交上线步骤；如果执行会话中用户已明确授权上线，则直接按步骤执行，无须重复确认。提交、推送和发布按执行会话的明确授权处理。

## 3. 固定决策契约

### 3.1 范围与模式兼容

- `legacy`、`shadow`、`rescue` 保持原有行为，配置默认值不变。
- `primary` 接管统一增量入口中的合格新增、待聚类人脸，包括正常反馈流程明确重新入队且未锁定的人脸。
- 不扫描并重新分配全部已归属人脸；不得解除人工锁或扩大反馈重聚类范围。
- primary 同时控制增量身份归属及合并推荐的新决策；不能出现聚类已 primary、推荐仍混合 legacy 的状态。显式切回 legacy 时两者均恢复旧路径，shadow/rescue 的历史兼容行为单独保留并注明。
- 本次统一“组件与人物”“人物与人物”的身份匹配，不替换 embedding 或底层组件形成算法；人工合并仍由用户确认。

### 3.2 统一引擎与策略契约

从现有 matcher 和 profile similarity provider 提取一个实际共享的身份匹配核心。两种输入通过适配层提供规范化的身份证据：待聚类组件的人脸证据、已有人物的活动画像中心及代表人脸。不得为待聚类组件创建持久化假人物。

共用以下计算：模型/版本校验、候选召回与过滤、中心和代表人脸比较、证据聚合、原始身份分数、候选排序、负面约束及结构化原因。适配层只转换证据和身份标识，不另写评分公式。多中心数量、样本规模、低支持中心如何参与聚合必须明确，避免单个高分中心掩盖混合身份。

引擎返回原始分数及证据，不直接把 `AutoEligible=false` 当成“不可推荐”。结果至少明确区分：正常匹配、正常无候选、证据不足、硬约束冲突、技术不可用、输入无效。逐目标/逐对结果均有明确状态，禁止用空 map 或 bool 混淆无候选与失败。

上层仅应用两套命名策略：

| 策略 | 分数与证据要求 | 行为 |
| --- | --- | --- |
| 自动归属 | 较严格分数阈值、margin、中心稳定性和支持证据 | 满足要求才写入人物归属 |
| 人工推荐 | 较宽分数阈值及证据要求；不足以自动归属但有有效匹配证据时可推荐 | 输出分数、证据不足说明，等待人工确认 |

在相同规范化输入、候选集合和引擎版本下，两种策略取得相同的原始分数、证据和硬约束；只能因策略阈值/证据门槛产生不同接受结果。不能为让推荐看起来更好而重新缩放或另算分数。人物对比较应对交换输入保持分数/约束一致；候选集合不同导致的 margin 差异要可解释，不强行比较不同召回上下文的 margin。

将分数阈值、margin、最低支持证据等策略参数集中定义和校验，分数门槛满足推荐不高于自动归属。整理原配置到新策略的映射；未经依据不直接照搬 legacy 分数阈值，也不擅自降低自动归属要求。记录生效策略版本/配置指纹。

人工 cannot-link 和经现有规则判定的同照片共现冲突在两条链路均硬阻断，不作为低门槛普通推荐。负证据无法读取时属于不可用，不能当作“没有冲突”。低支持/不稳定证据可用于带说明的人工推荐，但无效向量、失败的必要验证或不可用数据不算有效证据。不得新增自动解除人工约束行为。

### 3.3 primary 决策表与故障行为

| 引擎结果 | 增量聚类 | 合并推荐 |
| --- | --- | --- |
| 有明确目标且满足自动策略 | 按画像目标归属，即使旧算法意见不同 | 达到推荐策略则正常推荐 |
| 有有效证据，仅满足推荐策略 | 待定并有界退避 | 给出候选及证据说明 |
| 正常完成且无候选 | 沿用创建新人物/待定规则，保留跨照片和组件大小限制 | 正常无推荐 |
| 有候选但分数、margin 或稳定性不足 | 待定，不通过创建新人绕过不确定结果 | 仅满足推荐策略才显示，否则无推荐 |
| cannot-link、同照片共现硬冲突 | 拒绝本次归属，不自动选择次佳绕过冲突 | 不生成该冲突人物对的推荐 |
| 索引、画像、负证据不可用，数据库读取失败或 matcher 技术失败 | 等待恢复、退避重试，记录原因 | 明确等待/失败原因，不伪装成“无推荐” |
| 无效输入、未知原因、矛盾结果、NaN/Inf | 安全拒绝并记录异常 | 不生成候选，显示可诊断状态 |

primary 的两条链路均禁止调用旧算法作为隐式替代，包括整批、逐目标、逐对、medoid 验证失败和空候选回退。旧算法只在用户显式选择兼容/回退模式时承担业务决策，或在隔离的只读对照评估中使用。

待定采用有界退避，避免忙循环。画像/索引恢复后自动恢复正常处理；不能因为技术故障耗尽语义匹配重试次数，永久丢弃待处理人脸。无效输入可进入可诊断失败状态。不得用重试次数逐步降低 primary 阈值。

推荐任务部分目标不可用时，保留有效结果并明确“部分完成/待重试”及覆盖数量，重试只处理必要目标；不能将不完整结果标成完整成功。复用现有任务状态基础设施，按需扩展。

### 3.4 推荐持久化与审核一致性

- 新推荐持久化引擎版本、策略版本/配置指纹、画像版本或可验证证据标识、分数、原因和实际来源；primary 新生成推荐中 legacy 来源必须为零。
- 切换后已有旧算法/混合来源待审推荐保留历史记录并标识过期，不冒充新推荐。审核列表排除过期项或展示需刷新状态，按目标有界重新生成；不能清除已有人工接受/拒绝反馈。
- 接受推荐时重验人物存在、画像/归属版本和硬约束；证据变化时重新用同一引擎及推荐策略评估，失效则拒绝执行并提示刷新。人工接受不要求达到自动归属阈值。
- 复用现有人工合并写入和反馈链路。本任务的批次撤销仅撤销自动聚类，不能撤销用户已确认的推荐合并；后者必须使相关自动归属记录的撤销资格失效。
- 对现有审核界面做必要的小改动，显示等待/部分失败/过期原因以及推荐证据说明；无需新建管理平台。

### 3.5 计算、写入与画像失效

- 每个组件正常路径只调用一次画像 matcher，结果供写入和遥测复用。
- primary 运行路径不计算旧算法兜底；只读对照评估与实际决策分开。记录旧算法是否计算，不能把“未计算”记为 miss。
- 推荐复用同一引擎的批量能力、缓存和有界召回，避免逐候选 N+1 查询。召回预算差异必须显式传入且不能改变核心打分公式。
- 保持现有 coordinator / write gate 锁序，匹配计算不占用 SQLite 写事务。
- 写入时重验目标存在、组件资格和并发版本；组件内任一人脸冲突则整组件跳过或重试，不部分挂靠。
- 归属更新与撤销日志必须同事务成功；日志失败则本次归属不能提交。遥测仍可 best-effort，二者责任分开。
- 成功后走现有统计、缓存及画像 dirty 失效机制；失败恢复应最终可重试，不在持有 SQLite 写事务时重建画像。

## 4. 完整归属记录与批次撤销

### 4.1 数据设计

新增独立批次及逐人脸变更记录，或证明复用结构能满足全部要求。至少包含：

- 批次 ID、组件/操作 ID、时间、运行模式、算法版本、有效配置指纹、执行状态。
- 每个人脸 ID、原/新人物 ID、原/新聚类状态、分数、聚类时间、受本次操作影响的重试字段，以及撤销所需版本。
- 实际决策来源：画像挂靠、创建新人物；对应分数、margin、原因与索引代次。新建人物 ID 可追踪。
- 撤销结果、跳过原因、关联原操作；日志不可采样或截断，不能随普通遥测清理一起删除。

定义批次边界：一个 coordinator 增量批次对应一个可追踪批次 ID；事务可以按组件有界提交。崩溃后能区分已提交组件与未完成部分，不得把整批标成成功。进程重启后的补偿或状态收敛必须有测试。

实现单调递增的归属/人工修改版本或同等可靠机制。所有会影响撤销资格的后续写入都必须使旧记录失效，包括人工确认同一个人物、移走再移回、合并、拆分、解除归属和排除。只比较当前 `person_id` 或时间戳不足以识别这些情况。

primary 批次中的实际归属写入均纳入记录，包括画像挂靠和新人物创建。普通待定重试不必逐次保存完整归属快照，但其计数和原因必须可观测。

### 4.2 最小可用操作入口

本期实现管理员 API 或接入现有管理 CLI，选一种即可；批次撤销无需新增前端页面。写入必须经过后端服务协调，不允许 CLI 绕过运行中的服务直接修改生产 SQLite。

提供并文档化：

1. 列出/查询批次及实际归属记录，分页、有界输出。
2. 按批次预演撤销，显示可撤销、后续变更冲突、已撤销、目标已删除等数量和原因。
3. 显式执行指定批次撤销；默认预演，重复执行幂等，不能隐式撤销所有批次。

执行时再次检查版本，不能信任预演结果。以原组件为原子单位：任一成员被后续修改，则跳过整个组件并说明原因，保护人工修改和组件一致性。

撤销恢复原归属和本次变更的聚类字段，并推进版本，不能恢复旧版本号。原人物已不存在时跳过，不自动复活或合并人物。本次创建的人物只有在确认无人脸且无后续人工/引用变化时才可按现有安全规则清理；否则保留并报告。

撤销前暂停新增聚类写入并等待正在运行的批次排空。撤销后刷新相关统计、头像选择、缓存和画像，并防止立即重新入队抵消撤销；操作文档说明何时恢复调度和选择哪个模式。不能破坏人工反馈历史，也不能通过整库恢复覆盖上线后的其他用户修改。

## 5. 最新基线与副本验证

在能连接 NAS 时先只读检查实际版本、模式、运行时间窗口、画像 ready/dirty/failed、队列、错误和锁等待；报告必须标明采集时间。

检查近期实际自动归属、人工纠正及新旧分歧；无法将反馈可靠关联到自动归属时，标记“未知”，不要推导准确率。人工合并建议接受率不能代替自动聚类准确率。旧评估的样本数不是当前数据。

完整报告及重查询放在数据库副本上运行，先检查现有 `make backup-nas` / `scripts/backup-nas.sh` 的配置和行为。不得复制正在写入的裸 SQLite 文件作为一致性备份；不要输出凭证、embedding 或照片完整路径。

在同一副本、相同待处理样本及配置下比较 rescue 与 primary；每次从相同副本起点开始，隔离 worker 和生产连接。输出处理数、画像挂靠/新建/待定/技术不可用分布、目标分歧及有限案例、耗时、吞吐和锁等待。同时比较旧推荐与统一引擎推荐的候选变化、分数/证据、硬阻断数量、不可用覆盖和来源，抽查两条链路的一致性。无代表性样本时明确限制，仍完成合成测试及实现。

## 6. 测试要求

新增或调整针对性测试，至少覆盖：

1. 旧算法匹配 A、画像合格匹配 B，primary 实际写 B；rescue 仍写 A；shadow 不采用 B。
2. 正常无候选仍可按原条件创建新人；不满足条件继续待定。
3. 决策表中的所有阻断分类，特别是负证据不可用、无效输入、未知原因不会走宽泛兜底。
4. 技术故障下两条链路都不调用 legacy；空候选、无活动画像、medoid 验证失败、负证据读取失败均正确分类，恢复后继续处理。
5. 人工锁、manual/excluded 等不合格状态、非人脸和低质量人脸排除均不被绕过。
6. 单次 matcher 调用、目标并发消失、组件成员并发变化、日志插入失败和事务中断不会造成部分归属。
7. 日志保存完整组件（包括超过旧遥测截断上限的情况）；多个组件部分完成后进程中断可正确识别已提交记录。
8. 撤销成功、重复执行、预演后并发修改、人工确认同一人物、移走再移回、已删除原人物、组件局部冲突和新建人物清理。
9. primary 写入及撤销后统计/缓存/画像失效链路正确；撤销后不会立即被同一任务重做。
10. 现有 legacy/shadow/rescue 等价性与 coordinator 测试不回归；显式模式切换正确控制两条链路。
11. 相同规范化证据下两种策略原始分数/硬约束一致；人物对交换输入后分数一致。覆盖多中心、低支持中心和不同候选集合的 margin 语义。
12. 低于自动阈值但高于推荐阈值的案例仅推荐；cannot-link/同照片共现均不成为普通推荐；不能把 `AutoEligible=false` 全部过滤。
13. 推荐整批/逐目标/逐对不再隐式回退；primary 推荐来源无 legacy，部分失败不会显示完整成功。
14. 旧推荐失效与有界再生成，人工反馈保留；审核时画像变化、人物删除、新增 cannot-link 等使过期推荐无法直接执行。
15. 推荐等待、部分失败、过期与原因显示的 API/前端测试；避免明显 N+1 回归。

验证命令（仓库根目录下先 `cd backend`）：

```bash
go test ./internal/service ./internal/repository ./pkg/database ./pkg/config
go test ./cmd/relive-identity-profile-report
go test ./...
```

若新增 API/CLI，补对应测试；对实际改动的并发路径运行有针对性的 `go test -race`。只有修改前端才执行前端构建。本任务不能只依赖 fake matcher：聚类与推荐各保留使用真实统一引擎、约束和数据库的集成路径。区分既有失败、环境失败和本次回归，不能将未运行标成通过。

## 7. 迁移与上线操作文档

- 新表/索引及可能新增的版本字段需兼容现有 SQLite，迁移幂等，并在已有数据副本上验证。评估大表改动耗时，避免无谓全表回填。
- 不修改现有生产配置默认值，不通过部署顺带启用 primary。更新所有“primary 仍是 shadow-only”的过时注释和正式文档。
- 发布前列出执行版本、迁移、备份校验、配置位置、是否需重启以及验证命令；依据实际配置加载行为写，不假设热更新。
- 获得上线授权后：一致性备份并校验 → 部署迁移 → 切换 primary → 失效旧待审推荐并有界重新生成 → 恢复处理 → 检查真实归属和新推荐的引擎版本、来源与日志。
- 若当前没有合格待处理人脸，说明“已启用但尚未产生实际决策”，不得为制造证据自动重置历史数据。
- 分开记录“代码完成”“测试通过”“已部署”“已切换”“真实画像归属已发生”，不能只用 UI 模式值证明接管；另列“新推荐已使用统一引擎”的真实证据。
- 出现护栏绕过、日志与写入不一致、撤销损害人工修改、持续锁错误或不可恢复的队列阻塞时暂停切换/停止新增写入。效果问题报告具体案例和影响，由用户决定继续或回退，不设置没有依据的准确率门槛。
- 回退步骤：暂停并排空聚类 → 切回 rescue（或明确选择 legacy）→ 对问题批次预演撤销 → 按授权执行 → 核查统计和画像 → 将不兼容的待审推荐标记过期并按回退模式重新生成 → 恢复调度。切模式不会自动修复已经写入的归属。

## 8. 不包含

- 历史人物全量重聚类、批量解散或清空人物。
- 更换 embedding 模型、重新检测全库照片、重写底层聚类算法。
- 无依据降低自动归属阈值、重试自动放宽 primary 护栏、删除人工不能合并约束。人工推荐的独立较宽策略属于本任务范围。
- 恢复自动人脸质检；基础人脸检测、识别及人工“非人脸”“低质量人脸”排除继续保留。
- 将人物合并建议改为自动执行、重做前端或另建大规模评估平台。
