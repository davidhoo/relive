# 下线人脸质检模块，保留人物管理人工排除

> 实施时使用 superpowers:executing-plans，按本文任务逐项执行。本文是实施任务说明，不代表功能已修改或生产数据已迁移。

**目标：** 下线人脸质检页面及全部自动质检流程，保留从照片检测人脸、人物识别、聚类，以及人物管理中的人工排除功能。

**架构：** 将人工排除作为人物管理的独立能力保留，解除正常检测和人工排除对质检服务的依赖。历史自动质检结果通过可预演、可核对、可回滚的数据迁移退出业务判断；人工决定优先，来源不明不擅自恢复。

**技术栈：** Go / Gin / GORM / SQLite，Vue 3 / TypeScript，Python ML 服务。

## 一、已确认的产品边界

### 必须保留

| 能力或状态 | 计入照片人脸数 | 参与人物识别和聚类 | 说明 |
|---|---|---|---|
| 普通有效检测结果 | 是 | 按现有正常规则 | 保留基础检测、特征提取与识别流程 |
| 人工排除：非人脸 | 否 | 否 | 保留人物管理中的选项 |
| 人工排除：低质量人脸 | 是 | 否 | 是真实人脸，仅不用于识别 |

- 保留“人物管理 → 人脸 → 排除”的两个选项及操作路径。
- 保留人工撤销排除能力；恢复后回到正常待识别状态，不保证恢复旧人物归属。
- 正常重检照片时继续应用有效人工排除。此要求不意味着本任务要执行全库重新检测。
- 保留已有人工确认的人物归属、人物名称、人工锁定，以及其他正常识别结果。
- 质检页面中已经做出的有效人工排除也要保留，不能随模块一起删除。

### 必须下线

- 独立人脸质检页面、导航、审核与校准入口。
- 实时自动质检及独立验证器对检测结果的放行、排除、待审核裁决。
- 历史质检回填、校准、重评、自动隔离，以及任务创建、继续、重试和启动恢复执行。
- 正常业务对旧自动质检判定的依赖。

### 不包含

- 不关闭照片人脸检测、基础置信度准入、特征提取、人物识别和聚类。
- 不修改现有截图等照片级处理规则，不重做识别算法或调整阈值。
- 不删除照片、基础人脸框、特征向量、缩略图和人物数据。
- 不执行全库重检、全局重聚类，不猜测恢复已丢失的人物归属。
- 不因下线模块删除基础识别中用于排序、头像选择等用途的质量评分。
- 首次交付不要求物理删除所有质检历史表、列或 ML 模型资产。
- 本文编写不包含实现、提交、推送、发布或生产数据库清理。

## 二、当前代码事实与风险

以下事实基于编写时本地代码，实施前须重新核对工作区和部署版本。

1. `backend/internal/service/face_exclusion.go` 的 `UpdateFaceExclusion` 直接更新 `face_exclusions` 和 `faces`，不自动创建人工质检事件。同理由的重复排除会提前跳过。
2. `backend/internal/service/face_quality_service.go` 的人工审核会写 `source=manual` 的质检事件，并修改同一套排除记录和人脸状态。
3. “已人工确认”按质检事件 `source=manual` 筛选，不是全部人工排除的完整名单；恢复自动隔离的操作也可能写 manual 事件，因此不能把所有 manual 事件都理解为人工排除。
4. 自动质检也会写 `face_exclusions`。该表当前缺少明确来源，不能仅凭排除理由、`manual_locked` 或是否存在人工质检事件识别人工排除。
5. 后台回填会创建 auto 事件，但这不证明原人脸排除由自动操作造成。存在 auto 事件，不能直接推导“可以恢复”。
6. `people_service.go` 实时检测中，质检模式即便是 disabled，后续验证状态仍可能强制转入 review_required。shadow 在实时链路也不等同于完全不影响业务。
7. 自动隔离清空人物归属，恢复通常只回 pending。只删事件不清排除状态，或只清状态不清排除记录，都会残留业务影响。

**结论：两个入口不是完全隔离。入口和审计记录不同，底层排除状态共用。禁止直接清空排除表或只保留“已人工确认”列表。**

**步骤：**

2. 先通过 SQLite `PRAGMA table_info(...)` 核对实际表结构，再查询数据；不要照搬推测字段。
3. 统计人脸状态、排除理由、质检事件来源、当前事件和任务状态；同时检查原人脸被重检替换后的记录关联。
4. 结合可用事件、时间线、历史版本与备份，将迁移对象划分为：有效人工决定、可靠证明的纯自动影响、来源不明或冲突。

**硬约束：**
- 无 manual 事件不等于没有人工操作；有 auto 事件不等于排除由自动造成。
- 最新有效人工操作优先；已被撤销的人工排除不能复活。
- 人工在自动排除后再次确认同理由，旧代码可能未留下新记录；无足够证据时归入来源不明。
- 来源不明保留当前状态并在交付中明确列出，不得混入“清理完成”的数量。

**步骤：**

2. 将人工排除的持久化、恢复、重检匹配、统计同步及缓存失效保留在人脸管理链路，不能依赖待移除的质检服务。
3. 建议在 `face_exclusions` 增加明确来源字段，取值 manual / auto / unknown；历史默认 unknown，禁止默认 manual 或自动推定来源。迁移方式遵守仓库数据库惯例。
4. 新人工操作明确写 manual；即便已经同理由排除，也要记录此次人工确认，不能因幂等跳过而丢失来源。
5. 将已核实的有效人工质检排除转存到独立人工排除记录；保留必要的来源依据，保证模块下线后仍生效。
6. 处理人工恢复的最终意图，避免旧质检事件或旧 bbox 记录重新施加已撤销的排除。
7. 继续使用现有 bbox 匹配规则，不在本任务修改匹配阈值；覆盖重检导致 face ID 改变的测试。

**验收：** 人物管理可以独立完成排除与恢复；质检服务完全未初始化时上述测试仍通过。

## 七、任务 5：实现可预演、可回滚的历史迁移

**建议新增：**

如仓库已有统一迁移工具，优先接入，不重复建设。

### 处理规则

| 数据 | 迁移行为 |
|---|---|
| 人物管理留下的有效人工排除 | 原样保留理由及业务效果，补齐可确认的来源 |
| 质检页有效人工排除 | 转存独立人工排除记录，保留业务效果 |
| 人工恢复/接受、人工人物归属 | 保留最终人工意图，不重新应用旧排除，不清人物归属 |
| 可靠证明仅由自动质检造成的排除 | 撤销对应排除记录及状态，无可靠归属依据时回 pending |
| 可靠证明仅由自动质检造成的待审核 | 回正常待处理状态；已有有效归属不得无条件清空 |
| 自动 accepted | 停止使用其质检结论；不批量清空正常人物归属 |
| 来源不明、记录矛盾 | 保留，输出待核对清单 |
| 旧质检任务与事件 | 归档保留，停止消费；活动任务使用现有合法终态标记退役原因 |

### 执行要求

1. 先完成数据库一致性备份并验证可恢复性。SQLite 使用支持 WAL 的一致性备份方式，不能只复制一个活动 `.db` 文件。
2. 在无并发写入的维护窗口执行 apply；升级后先确认不会启动旧 worker，再执行迁移，完成后恢复正常检测工作。
3. apply 必须校验预演时的记录状态或版本；发生变化时中止或重新预演，不能覆盖新人工决定。
4. 使用事务和幂等迁移标记，保留变更前镜像、实际变更清单和统计。失败可回滚，不出现半清理状态。
5. 迁移不得生成新的自动质检判断，不调用检测或复核模型。
6. 只重算受影响照片的人脸数及相关人物统计、头像、身份缓存和合并建议；禁止以“修统计”为由触发全库重聚类。
7. 先在数据库副本验证，再报告线上预演结果。生产写入应在具体清单和备份可审查后单独获准，本任务文档不等于生产清理授权。

## 八、验证与交付证据

### 自动测试矩阵

- 两种人工排除：计数、识别、聚类、恢复、重启、重检后状态正确。
- 人工与自动混合历史、人工重复确认同理由、人工撤销后旧记录残留、face ID 更换。
- 仅有 auto 回填事件不能被判定为纯自动排除；来源不明不会被恢复。
- 质检服务缺席和旧 enforce 配置下，正常照片检测、特征提取、人物归属继续工作。
- 活动及暂停质检任务不会重启；旧接口调用不能启动工作。
- 迁移预演零写入、重复执行幂等、并发状态变化被拒绝、事务失败可回滚。
- 正常人物归属、人工锁定和基础检测数据不被迁移误改。

## 九、部署与回滚

推荐顺序：完成实现与测试 → 副本迁移验证 → 线上只读预演 → 审查具体影响清单 → 维护窗口一致性备份 → 部署下线代码并确认旧 worker 不运行 → 应用迁移 → 验收 → 恢复正常业务。

- 代码与数据库回滚必须配套，防止旧代码再次消费历史任务或自动质检事件。
- 不应简单回退旧二进制并用 disabled 配置启动；旧开关不足以阻止全部质检。准备保留“禁止自动质检启动”保护的回滚版本，或保持服务停止直至方案验证。
- 维护窗口内可从一致性备份恢复；恢复业务写入后，禁止直接覆盖整库而丢失新数据，应采用经验证的逆向迁移或另行安排恢复窗口。

## 2026-09-08 审查修复补充

- 正常重检创建替代人脸后，在同一事务更新匹配排除记录的 `source_face_id`，确保后续人工恢复能删除对应记录。
- 对旧版本留下的、指向已删除人脸的排除记录，恢复时仅处理同照片下唯一且不与其他现存脸冲突的 bbox 匹配；歧义时拒绝操作，保留原状态。
- 迁移遇到匹配其他 face ID 的排除记录时归为 unknown，不凭当前 auto 事件将替代人脸恢复为 pending。
- apply 必须读取之前审查的预演文件，事务内重新检查完整对象集合及动作字段；新增、删除、状态变化、重复项目或编辑后的动作均拒绝执行。实际执行数据库重新计算且校验一致的动作。

迁移工具用法（先在数据库副本中验证）：

```bash
# backend/ 下执行；预演文件必须使用新路径，避免覆盖已有文件。
go run ./cmd/retire-face-quality -db /path/to/copy.db -out /path/to/approved-plan.json

# 审查后，执行同一份清单；数据库若发生变化则重新预演和审查。
go run ./cmd/retire-face-quality -db /path/to/copy.db -apply -plan /path/to/approved-plan.json -mirror /path/to/apply-plan.json
```

`-mirror` 保存的是本次提交执行的计划副本，不是数据库备份，不能替代前述 WAL 安全一致性备份。输出路径必须不存在，且不能覆盖输入数据库或已审查计划。本次修复不包含生产迁移、发布或合并。
