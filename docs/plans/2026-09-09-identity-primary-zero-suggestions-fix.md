### 2.3 已发现的实现缺口

1. `identity_matching_engine.go` 的 `MatchComponent` 仍调用原 `IdentityProfileMatcher.Match`；人物比较调用新增 `ScoreIdentityEvidence`，尚未真正统一评分核心。
2. 新人物评分取双向覆盖的较低值，推荐阈值仍来自既有 `MergeSuggestionThreshold`。不能假设新旧评分分布等价，也不能直接认定阈值是唯一问题。
3. `SimilarPeople` 把缺少目标画像中心映射为 `no_candidate`；候选无证据和配对计算不可用也可能被静默丢弃，无法区分故障与有效空结果。
4. `primaryAssignments` 仅暂写 partial 文案，最终仍返回普通 assignments 与 nil error；外层切片推进 cursor、保存空结果，结束后写 `dirty=false` 和“本轮巡检完成”。错误状态和重试责任没有保留。
5. `recallPersonCandidates` 将候选按人物 ID 排序后截断 200，可能损失更相关候选；这不等于已证明它导致本次前三对丢失，必须单独验证。

## 3. 工作一：先复现候选丢失，形成可检验的根因

核对本地提交、部署二进制构建来源、启动配置路径及有效策略参数。NAS 上遗留源码目录不能当作正在运行二进制的源码证明。本轮发现该目录缺少新引擎文件，但实际二进制包含新引擎符号，必须区分二者。

提供可重复的**只读诊断入口**，优先在一致性数据库副本上运行。复用生产引擎、service 决策及 repository 查询，禁止只手抄一份相似算法作为最终复现证据。运行前说明范围与成本，按目标 ID 限定；不触发生产任务、不调用写入 API、不把诊断结果写入生产推荐表。

对表中两目标四候选输出逐阶段结果：

1. 目标是否入选本轮巡检，cursor 与分页范围、category/hidden/face_count 等资格。
2. 目标/候选画像状态、活动 generation、模型签名和证据数量。
3. 索引是否 ready、索引代次及 relevant invalid/delta 状态；候选是否被召回、召回/截断位置。
4. 精确评分、双向分量、支持证据、硬约束与策略接受/拒绝原因。
5. `bestByCandidate` 分配竞争、目标批次之间去重及替换是否使其丢失。
6. 传给 `ReplacePendingForTarget` 的条目、事务结果以及后续 obsolete/清理/失效操作。
7. pending 查询、来源/版本校验和展示过滤结果。

先把“在哪一步丢了”落实为回归测试，再修对应路径。若副本复现与线上仍不同，应交付最小有界运行诊断支持，在获准部署后取得真实阶段证据；不得用猜测补全运行内存状态。不能只交付更多日志而结束整个修复。

阶段统计至少区分：入选目标、有效画像、无有效画像、召回候选、精排候选、硬阻断、低于推荐阈值、证据不足、技术不可用、策略接受、最终写入、被替换/过期。每阶段计数标明单位（目标或人物对），能解释差额；不输出 embedding、图片路径或凭证。

## 4. 工作二：真正统一身份评分并校准策略

从组件及人物输入适配出规范化证据，进入**同一套实际打分、证据聚合和约束核心**。共用接口或 cosine 工具函数不算完成统一。适配层不偷偷另算分数。

- 相同规范化证据及候选上下文，原始分数、证据和硬约束必须一致；自动归属与推荐只因阈值、margin、稳定性/支持证据要求及执行方式不同而产生不同结果。
- 人物对评分保持交换输入对称；组件输入保留真实质量权重和全部必要的身份限制，不为适配而创建假人物或解除人工锁。
- 不直接把“人物双向全覆盖取最小值”不加验证地强加到组件聚类。用真实代表样本说明：同一人物不同年龄、角度和小样本子集如何匹配，多中心混合身份又如何避免误合并。
- 不以要求小候选覆盖大人物所有外观中心作为未经论证的必要条件，也不能退化为仅凭一个最高分中心就自动归属。记录最终聚合选择、权重与证据要求，并通过正负样本验证。
- 中心/支持信息必须真实传递，不能把 `MinSupportCount` 等写死为 1 或用占位值通过策略。当前映射存在该写法，需检查其与默认最小支持数 3 的冲突，避免自动聚类整体被额外阻断。
- 明确人工不能合并及现有硬冲突在两条链路一致；不恢复旧算法隐式兜底。

在同一副本和固定样本上比较旧评分、当前问题版本、修复评分的分布及业务判断。上述四对仅用于链路测试；阈值校准需包含已有人工确认/拒绝样本，并标明反馈是否能可靠关联。没有可靠标签时说明限制，不编造准确率。

推荐阈值不高于自动阈值；自动执行保留更严格的 margin 和证据要求。若改变评分语义或阈值来源，提升引擎/策略版本及配置指纹，给出现配置迁移映射和建议值的证据。不能只提交 `0.55 → 某个更低数值` 的补丁。

## 5. 工作三：修复候选召回、状态与持久化

### 5.1 候选召回

- 审查 ANN 按中心召回后人物去重、invalid/generation 过滤及截断，确保召回排序与精排目标尽量一致。
- 修复按人物 ID 任意截断的问题；ID 仅用于同分稳定排序，不能决定谁进入前 200。
- 对第四对做有界精确召回对照，量化重建前后和多次建图的召回差异。若选择扩大召回、补充精确检索或分批候选策略，给出上限和性能依据；禁止把生产全库两两比较作为常规解决方案。
- 新引擎不可用时等待恢复，不走 legacy 回退。

### 5.2 状态与重试

- 无有效目标画像、dirty/failed 或必要数据读取失败，必须与“有效画像正常召回为空”分开。必要证据不可用不得解释为匹配失败或零推荐。
- 明确逐目标和逐候选失败如何影响目标完整性：已有有效结果可保留，但部分计算失败不能把整目标标成完整成功。
- 完整成功且确实无建议，才允许以正常空结果替换该目标待审建议。不可用不能以空结果删除已有建议；历史建议若证据过期，应标明需重验，不能继续无条件接受。
- 用结构化结果传递失败集合及可重试原因，持久化足够的重试状态。不能只写 `CurrentMessage` 后返回成功。
- 巡检主 cursor 可以继续处理其他目标，但失败目标必须进入有界重试集合；重启后不丢失。存在未处理失败时不能清空 dirty 并显示完整成功。
- 恢复后重试必要目标，防止忙循环；技术失败不消耗身份不匹配的重试额度，不必须等下一次 24 小时巡检才能恢复。
- 前端显示完成、部分完成、等待画像/索引、失败及相应数量，复用现有任务界面，做必要小改动。

### 5.3 推荐持久化与审核

- 审查 `buildItemsFromBest` → `ReplacePendingForTarget` 是否完整保存引擎版本、策略版本、配置指纹、画像代次、原因及来源。当前 repository 创建记录时字段复制不完整，须补测试验证真实数据库值，不能只检查内存对象。
- 自动去重、跨目标替换或过期操作必须可解释且事务一致，不能静默丢失已接受候选。
- 旧版本建议保留历史、标记失效并有界再生成；保留人工确认/拒绝反馈。审核时重验版本和硬约束；人工接受仍使用推荐门槛，不要求达到自动归属门槛。
- 不自动合并本次排障的四对人物，也不把新建议自动执行。
